# Blueprint Agent 요구사항 정의서 (v2 — 단일 고객 모드 / AI-DLC 입력 생성기)

> **v2 재검토 요지**: 산출물을 **목업 HTML · requirements.md · constraints.md 3종으로 한정**하고, 콘솔을 **단일 고객 모드**로 다이어트한다. 코드 생성·SRS/ERD/OpenAPI·개발자 모드·계약의 사용자 노출을 제거한다. 시각 계약(freeze)은 **내부 엔진**으로만 유지(문서를 결정적으로 근거짓기 위함). **개발 작업 방식(§5)은 기존과 동일하다.**

## 1. 프로젝트 개요

### 1.1 서비스 비전

회의에서 오간 말을, 사람이 눈으로 확인·확정하는 순간에, 다음 개발 단계(AI-DLC)가 **그대로 입력으로 삼을 수 있는 문서 세트**로 변환한다. 결과물은 이해관계자가 검토한 **화면(목업)** 과, 그 화면에서 근거를 잃지 않고 도출된 **requirements.md · constraints.md** 다. 즉 Blueprint Agent는 **"회의 → AI-DLC 입력 패키지" 생성기**다.

### 1.2 해결하려는 문제

**문제 1 — 요구사항 오해로 인한 재작업**
텍스트 요구는 이해관계자마다 다르게 읽히고, 그 차이는 구현이 끝난 뒤에야 드러난다. 회의 중 나온 말을 즉시 화면으로 만들어 오해를 회의 자리에서 발견한다.

**문제 2 — 다음 단계로 넘길 입력을 사람이 손으로 정리하는 비용**
회의 결과를 요구사항 문서로 정리하는 일은 느리고, 근거(누가 왜 말했는지)가 소실된다. 확정된 화면에서 문서를 자동 도출하되 발언까지 역추적 가능하게 한다.

**문제 3 — 근거를 잃은 생성**
자동 생성물이 "왜 이렇게 나왔는가"에 답할 수 없으면 검증이 불가능하다. 모든 산출물은 발언까지 이어지는 근거 사슬을 보존한다.

### 1.3 핵심 가치 제안

- **이해관계자**: 회의 중 말이 즉시 화면이 되고, 대화로 수정하다 "확정"하면 **AI-DLC에 바로 넣을 문서(requirements.md·constraints.md)** 가 나온다. 전문 문서 작성 능력이 없어도 된다.
- **개발자/후속 자동화**: 확정된 화면에서 **재현 가능하게** 도출된 요구·제약 문서를 받는다. 모든 항목이 발언까지 역추적된다.
- **시장 차별화**: 화면 생성 도구가 아니라, **화면을 매개로 "다음 파이프라인의 입력"을 결정적으로 도출하는** 시스템. 확정 화면을 모델 비용 0의 결정적 계약으로 굳힌 뒤 문서를 뽑는다는 점이 구조적 차별점이다.

### 1.4 시스템 불변 원칙

전 기능에 우선한다. 어떤 기능도 위반할 수 없다.

**원칙 1 — 원본 화면 마크업 격리**
언어 모델은 화면 마크업 원본을 소비하지 않는다. 원본은 정해진 변환 지점(확정·계약 추출)에서 단 한 번만 접촉되고, 이후 문서 도출은 정규화된 중간 표현(시각 계약)과 회의 발언만 입력으로 받는다.

**원칙 2 — 확정 단계의 결정성**
화면을 시각 계약으로 변환하는 단계는 언어 모델을 쓰지 않는다. 동일 입력은 언제나 동일 출력을 낳고, 이 단계의 모델 호출 비용은 0이다.

**원칙 3 — 근거 없는 생성 금지 (강화)**
requirements.md는 발언·계약에 없는 요구를 추가하지 않는다. constraints.md는 **발언에 명시된 제외/비목표만** 담거나, 사용자가 명시적으로 확정한 항목만 담는다. AI가 임의로 제약을 지어내지 않는다. 화면은 브리프에 없는 요소를 추가하지 않는다.

**원칙 4 — 근거 보존**
모든 산출물은 자신이 파생된 상위 산출물과 그 근거(회의 발언)를 식별 가능한 형태로 함께 보존한다.

## 2. 서비스 구성

### 2.1 주요 구성 요소

- **작업 콘솔**: 이해관계자가 쓰는 **단일 화면(고객 모드 하나)**. 회의 대화 입력, 목업 미리보기, requirements.md·constraints.md 열람, 단일 실행 버튼을 담당.
- **파이프라인 처리 계층**: 요구 캡처 → 화면 공동 설계 → 확정 및 계약 추출(내부·결정적) → 문서 도출.
- **산출물 저장소**: 프로젝트별 목업 버전 이력, 확정 시점 계약(내부), 도출 문서, 근거 메타데이터를 파일로 영속 보관.

### 2.2 처리 계층 정의

| 계층 | 입력 | 출력 | 노출 | 모델 |
|---|---|---|---|---|
| 요구 캡처 | 회의 녹취 텍스트 | 요구 브리프 | 내부(목업 입력용) | 사용 |
| 화면 공동 설계 | 요구 브리프 | 의도 메타데이터가 부착된 목업 HTML | **산출물** | 사용 |
| 확정 및 계약 추출 | 확정된 목업 | 시각 계약 | 내부 엔진 | **미사용(결정적)** |
| 문서 도출 | 시각 계약 + 회의 발언 | **requirements.md · constraints.md** | **산출물** | 사용 |

**서비스가 사용자에게 내주는 산출물은 정확히 3종이다: 목업 HTML · requirements.md · constraints.md.**

## 3. 핵심 기능 요구사항

### 3.1 요구 캡처

#### 3.1.1 회의 녹취 입력
- 발언자 라벨(`발언자: 내용`) 형식 녹취 입력. 라벨 없는 줄도 하나의 발언으로 수용.
- 예시 녹취 템플릿 제공·선택 시 즉시 로드.
- **작업 중 추가한 발언은 영속되어(새로고침 후에도 유지) 이후 처리에 반영된다.**
- 발언은 채팅 버블로 시간순 표시, 발언자별 시각 구분.

#### 3.1.2 발언 식별 체계
- 각 발언에 문서 순서 기반 식별자(`u-001`)를 **모델 없이 결정적으로** 부여.
- 동일 녹취는 언제나 동일 식별자. 발언 추가 시 기존 식별자 불변.

#### 3.1.3 요구 브리프 추출 (내부 중간 산출물)
- 비정형 발언을 화면 목적 · 데이터 객체·필드 · 사용자 액션의 세 영역으로 구조화.
- 각 항목에 근거 발언을 `[근거: u-002, u-005]`로 태그. 발언에 없는 내용 추가 금지(원칙 3).
- 브리프는 목업 생성의 입력이며, **사용자에게 별도 산출물로 노출하지 않는다**(최종 요구는 requirements.md).
- 장시간 작업이므로 비동기 실행 + 상태 조회.

### 3.2 화면 공동 설계 (목업)

#### 3.2.1 목업 생성
- 요구 브리프로부터 단일 화면 HTML 목업 생성. 브리프에 명시된 요소만 생성(원칙 3).
- 모든 의미 요소에 **저자 의도 메타데이터**(`data-bp-*`: 컴포넌트 식별자·역할·데이터 바인딩·액션 정의)를 부착. 이는 §3.3 계약 추출의 필수 입력.
- 시각 규격은 `requirements/samsung-design-guidelines.md`를 따른다.
- 콘솔 내 즉시 미리보기 + 지정 해상도 등비 전체화면 확대. 진행 상태 실시간 표시.

#### 3.2.2 대화 기반 델타 수정
- 직전(최신) 버전 생성 시점 이후 **추가된 발언만** 델타로 추출.
- 수정 입력 = **직전 버전 화면 + 델타 발언에서 도출된 수정 브리프**로 한정. 근거(델타 발언) 없이는 수정이 발생할 수 없다(원칙 3 / 아래 C-4).
- 결과는 새 버전으로 기록(생성 모드 신규/수정, 부모 버전 포함).

#### 3.2.3 버전 이력 관리
- 프로젝트별·버전별 목업 영속화, 과거 버전 재로드·미리보기.
- 버전마다 보존: 생성 시각 · 모드 · 부모 버전 · 대화 스냅샷 · 근거 발언 목록(신규=전체, 수정=델타) · **요구 브리프 요약** · 모델 사용량.

### 3.3 확정 및 계약 추출 (내부 엔진 · 결정적)

> 이 계층은 **사용자에게 노출되지 않는다.** requirements.md를 확정 화면에서 재현 가능하게 근거짓기 위한 내부 단계다.

#### 3.3.1 시각적 확정 (Freeze)
- 사용자가 특정 목업 버전에 "확정"을 선언(단일 실행 버튼 흐름의 내부 단계로 수행 가능).
- 확정 시점 타임스탬프와 함께 산출물을 실행 단위로 보존.

#### 3.3.2 시각 계약 추출
- **언어 모델 없이** 결정적으로 추출(원칙 2 / C-1). 기하(렌더 위치·크기) + 구조(요소 역할) + 의도(§3.2.1 메타데이터)를 융합.
- 계약 필수 구성: 페이지 정보 · 데이터 객체 목록 · 컴포넌트 목록(경계상자·바인딩) · 액션 목록 · 상태 흐름.
- 동기 처리, 모델 비용 0.

### 3.4 문서 도출 (requirements.md · constraints.md)

**목적**: 확정된 시각 계약과 회의 발언으로부터, 다음 단계 AI-DLC가 그대로 입력으로 쓸 문서 2종을 도출한다.

#### 3.4.1 requirements.md 도출
- **입력은 시각 계약 + 회의 발언으로 한정한다.** 원본 화면 마크업을 입력으로 받지 않는다(원칙 1 / C-2).
- 산출: 화면 목적 · 데이터 객체·필드 · **기능 요구사항(`FR-01` 체계 번호)** · 사용자 액션을 담은 단일 Markdown 요구 문서.
- 각 기능 요구 항목은 근거가 된 발언(`[근거: u-XXX]`)·계약 요소를 병기하여 역추적 가능해야 한다.
- 비동기 실행 + 상태 조회. 콘솔에서 서식 문서로 렌더링.

#### 3.4.2 constraints.md 도출
- **발언에 명시된 제외·비목표만** 추출하여 `[근거: u-XXX]`로 태그(원칙 3). 근거가 없으면 항목 없이 "회의에서 확인되지 않음"으로 남긴다 — **임의 생성 금지.**
- 보완(선택): 콘솔이 흔한 제외 카테고리 체크리스트를 제시하고, **사용자가 체크한 항목만** `[사용자 확정]` 표시로 문서에 편입한다. AI가 몰래 추가하지 않는다.
- 산출: 제외 기능·설계 제약을 담은 단일 Markdown 문서.

### 3.5 추적성

- 회의 발언을 근거 원천으로 하는 추적 사슬을 유지한다.
  ```
  회의 발언 (u-XXX)
   └─ 목업 버전 vN (생성 시각·모드·부모·대화 스냅샷·근거 발언·브리프 요약)
       └─ 시각 계약 (확정 시점 고정, 내부)
           └─ requirements.md(FR-XX · [근거:u-XXX]) · constraints.md([근거:u-XXX] | [사용자 확정])
  ```
- 시스템은 "언제/누가/무엇이/왜 바뀌었는가"를 산출물만으로 답할 수 있어야 한다(버전 메타·대화 스냅샷·델타·근거 태그).

### 3.6 작업 콘솔 (단일 고객 모드)

> **화면 구성 정본: `requirements/redev-screen-spec.yaml`.** 디자인 규격 정본: `requirements/samsung-design-guidelines.md`.

- **단일 모드**다. 개발자 모드·모드 토글은 없다.
- **단일 실행 버튼**으로 다음이 자동 연속 실행: ① 요구 정리(내부) → ② 목업 생성 → ③ 확정·계약(내부) → ④ 문서 도출(requirements.md·constraints.md).
- 좌측: 회의 녹취 채팅 표시 + 발언 추가(영속). 발언 추가 후 재실행 시 §3.2.2 델타 수정.
- 우측: 산출물 뷰 전환 — **목업 · requirements.md · constraints.md** (+ 버전 이력).
- 모델 사용 처리는 비동기(작업 식별자 반환 + 상태 조회), 결정적 처리(확정·계약)는 동기.
- 진행 상황을 서버→클라이언트로 **세션 스코프 실시간 스트리밍**한다(타 세션 간섭 없음). 실패 시 사유 표시 + 이전 상태 보존.

## 4. MVP 개발 범위

### 4.1 필수 (핵심 파이프라인)
- 회의 녹취 입력·발언 식별·**녹취 영속화** (§3.1)
- 요구 브리프 추출(내부, 근거 태그) (§3.1.3)
- 목업 생성(의도 메타데이터) + 델타 수정 + 버전 이력 (§3.2)
- 시각적 확정·계약 추출 — 내부·결정적 (§3.3)
- **requirements.md · constraints.md 도출** (§3.4)
- 단일 고객 모드 콘솔 (§3.6)

### 4.2 제외 (v2에서 내림 — constraints.md 참조)
- 코드 생성, SRS/ERD/OpenAPI 개별 산출, 개발자 모드, 계약의 사용자 노출.

### 4.3 후순위
- 실시간 음성 인식(STT) — 미설치 시 나머지 기능 정상 동작.

## 5. 개발 작업 방식 요구사항

**목적**: 이 MVP는 AI-DLC 파이프라인을 다중 에이전트 플릿으로 병렬 개발한다. 작업 방식 자체를 근거 사슬(§3.5)과 동일한 원칙 — 누가·무엇을·어떤 근거로 — 아래 두어, 산출물이 어느 인스턴스의 어떤 작업에서 나왔는지 역추적 가능하게 한다.

### 5.1 팀 구성
- 작업자는 총 **5명**: 오케스트레이터 1 + 워커 인스턴스 4.
- **메인 오케스트레이터 겸 PM (jd, 로컬 세션)**: 조율·통합·게이트·판단을 담당한다. inception·계획·계약 수정 권한을 단독 보유한다.
- **워커 인스턴스 4대**: `suman` · `mingu` · `gyu` · `yudo`.
- **백업 (`ardr-dev`)**: 전면 배치에서 제외하며, 지정된 백업 조건에서만 투입한다.
- 각 인스턴스의 자원 등급·배분 무게·승계 순서 등 세부 정보의 **정본은 `/blue-agents` 스킬**이다. 이 문서는 정본을 참조하며 중복 서술하지 않는다.

### 5.2 역할 분리 — 오케스트레이터가 계약을 소유한다
- **메인 오케스트레이터(jd)** 가 다음을 단독으로 확정한다. 이것이 병렬 작업의 공유 인터페이스(계약)다.
  - 설계 (컴포넌트·모듈 경계와 의존 관계)
  - 데이터 계약 (슬라이스 간 공유되는 데이터 모델·타입)
  - API 명세 (경로·동사·요청/응답 형태)
- 워커 인스턴스는 계약을 **소비**할 뿐 수정하지 않는다. 계약 변경이 필요하면 오케스트레이터에 **제안**만 하고, 반영 여부는 오케스트레이터가 결정한다.

### 5.3 브랜치 모델
- `main` — 통합 대상. 동결된 설계·계약의 정본.
- `jd` — 오케스트레이터 전용. 설계·계약·API 명세 수정은 이 브랜치에서만 하고, 확정 시 `main`에 머지한다.
- `feat/<worker>` — 슬라이스별 1개. 항상 최신 `main`에서 분기한다.

### 5.4 원자적 슬라이스 병렬 프로세스

**핵심 원칙**: 오케스트레이터가 계약을 확정한 뒤 구현을 **정확히 4개의 원자적 슬라이스**로 분해하여 워커 인스턴스 4대에 1:1 배분한다. 각 슬라이스는 계약 동결 이후 다른 슬라이스의 완료를 기다리지 않고 독립적으로 완결 가능해야 한다(원자성). 슬라이스 경계와 매핑은 AI-DLC inception(Units Generation)이 정하며 고정이 아니다.

**수명주기 (상태 전이)**:

```
[1] 계약 확정   오케스트레이터가 설계·데이터 계약·API 명세를 확정 (jd → main)
      │
[2] 동결·배리어  4개 슬라이스 전부 계약 ACK(READY) 이후에만 구현 시작.
      │          한 슬라이스라도 ACK 전이면 전체 대기.
      ▼
[3] 병렬 구현    4개 슬라이스를 4개 인스턴스가 동시 진행. 상호 대기 없음.
      │
      ├─ 진행 불가 선언(HOLD) ─────────────────────────┐
      │   어느 슬라이스든 계약 결함으로 진행 불가를        │
      │   선언하면 **전체 작업을 즉시 일시정지**한다.      │
      │   오케스트레이터가 계약을 개정(jd 브랜치)하고      │
      │   재동결한 뒤 [2] 배리어부터 재개한다.            │
      │                                                │
      │◄───────────────────────────────────────────────┘
      ▼
[4] 완료         이슈 없는 슬라이스는 끝까지 진행하여 각자 완결
      │
[5] 통합         전 슬라이스 완료 후 오케스트레이터가 `feat/<worker>`를
                 `main`으로 통합하고 게이트를 실행한다
```

**규칙 요구사항**:
- **전역 일시정지**: 슬라이스 하나의 진행 불가 선언은 개별 슬라이스가 아니라 **전체 작업**을 멈춘다. 계약이 개정되면 전 슬라이스가 재동결된 계약으로 다시 시작하거나 이어간다.
- **근거 없는 진행 금지**: 계약이 동결되지 않은 상태에서는 어떤 슬라이스도 구현을 시작하지 않는다.
- **통합 시점 일원화**: 워커는 자신의 슬라이스만 완결하고, `main` 통합·게이트는 오케스트레이터만 수행한다.
- 상세한 정지-수정-재개 규율은 `parallel-atomic-dev` 스킬을, 인스턴스 배분·승계·하달 절차는 `/blue-agents`(정본)를 따른다.

### 5.5 작업 추적
- 한 슬라이스는 한 인스턴스가 담당한다. 같은 슬라이스를 두 인스턴스에 걸치지 않는다.
- 인스턴스 이탈 시 승계 순서(`gyu → yudo → ardr-dev`)에 따라 살아있는 인스턴스가 해당 `feat/<worker>` 브랜치를 이어받는다.
- 취합 보고는 **어느 인스턴스가 어떤 슬라이스를 수행했는지, 전역 정지 발생 여부와 사유, 승계 여부**를 명시한다.

### B. 용어 정의
- **요구 브리프**: 발언을 화면 목적·데이터·액션으로 구조화한 **내부** 중간 산출물(목업 입력용).
- **저자 의도 메타데이터**: 목업 각 요소에 부착되는 기계 판독용 정보(`data-bp-*`).
- **시각 계약**: 확정 화면을 기하·구조·의도로부터 결정적으로 추출한 **내부** 기계 판독 문서. 문서 도출의 유일한 화면-측 입력.
- **산출물(3종)**: 목업 HTML · requirements.md · constraints.md.
- **근거 사슬**: 회의 발언에서 시작해 각 단계가 상위 근거를 보존하는 파생 관계.

### C. 상충 시 우선순위
기능 요구가 §1.4 불변 원칙과 상충하면 **불변 원칙이 우선한다.** 특히:
1. 확정·계약 추출에 모델을 도입해 결정성을 훼손하는 설계.
2. 문서 도출에 원본 화면 마크업을 입력으로 추가하는 설계.
3. 근거 없는 보완(특히 constraints.md의 임의 제약)을 허용해 추적 사슬을 끊는 설계.
