## 1. 개요

### 1.1 제품 정체

Blueprint Agent는 **AI-DLC 사이클의 앞단 — requirements·constraints 작성 — 을 고도화하는 제품**이다. AI-DLC는 요구를 구조화된 산출물로 내려보내며 개발을 진행하지만, "회의에서 오간 말"을 "AI-DLC가 소비할 수 있는 요구·제약"으로 정리하는 그 앞단은 비어 있다. 이 제품이 그 빈 영역을 채운다.

이 제품 자체도 AI-DLC로 개발되어 대회에 출품된다. 즉 **우리는 AI-DLC로, AI-DLC의 앞단을 만든다.**

### 1.2 문제·사용자 (누구의, 어떤 문제를, 언제, 얼마나 자주)

**해결하는 문제 — 요구사항 오해로 인한 재작업.**
소프트웨어 개발에서 가장 비싼 재작업은 "만들고 나서야 요구가 잘못 이해됐음을 발견하는 것"이다. 텍스트 요구사항은 이해관계자마다 다르게 읽히고, 그 차이는 구현이 끝난 뒤에야 드러난다.

**대상 사용자.**
프로젝트 초기 **아이디에이션 회의에 함께 앉은 기획자 · PO · 개발자**. 이들은 한 화면 앞에서 토론하며 많은 의사결정을 내린다.

**언제·얼마나 자주 아픈가.**
- **언제**: 프로젝트가 시작되는 아이디에이션 단계, 요구가 아직 말(speech)로만 존재하는 시점.
- **얼마나 자주**: 프로젝트마다, 그리고 프로젝트 안의 **회의체마다** 반복된다.
- **통증의 실체**: 오늘 가장 빠른 피드백 루프는 "동작하는 MVP가 나온 시점"이다. 그런데 그 시점에서 오해를 발견하면, MVP 개발에 쓴 **토큰·시간이 이미 낭비된 뒤**다. 오해는 회의 자리에서 이미 생겼는데, 확인은 개발이 끝난 뒤에야 가능하다는 시차가 재작업 비용의 근원이다.

**우리의 접근 — 피드백 루프를 회의 단계로 당긴다.**
"동작하는 것을 봐야 오해가 드러난다"면, **회의 자리에서 볼 수 있는 것을 즉시 만들어** 오해를 그 자리에서 드러낸다. 말 → 정리된 요구·제약 → 사람이 눈으로 확인하는 목업 → 다시 요구·제약으로. 이 루프를 개발 착수 **이전**에 돌려, MVP를 만들기 전에 오해를 소진한다.

### 1.3 골든패스 (이 제품의 핵심 흐름) ★

```
회의 대화 입력(텍스트·음성)
   └─ requirements · constraints 정리(추출)        [모델]
       └─ 목업(HTML) publish — 사람이 눈으로 확인   [모델]
           └─ 피드백 이터레이션: 대화로 요청 → 고도화(develop) → 목업 republish   (반복)
               └─ freeze — 만족한 시점을 major 버전으로 고정
                   └─ export — req·constraints 확정본 + 목업 + 근거 추적 메타
                                (export 시점에 목업에서 시각 계약을 결정적으로 추출)
```

- **원천은 requirements·constraints이고, 목업은 그로부터 나온 파생 뷰다.** 피드백은 목업을 직접 편집하는 것이 아니라 대화·요청으로 들어와 요구·제약을 고치고, 목업은 거기서 다시 렌더된다.
- 이 골든패스가 end-to-end로 동작하는 것이 제품의 존재 증명이다(§6).

### 1.4 시스템 불변 원칙

아래 원칙은 전 기능에 우선한다. 어떤 기능도 이를 위반하지 않는다. 상세 제약은 `constraints.md` C-1~C-6과 대응한다.

- **원칙 1 — 원천은 requirements·constraints, 목업은 파생물.** 목업 편집이 원천을 바꾸지 않는다. 하류로 나가는 것은 목업 원본이 아니라 시각 계약이다. (↔ C-2)
- **원칙 2 — 근거 없는 생성 금지.** 요구·제약은 대화에 없는 내용을 추가하지 않고, 목업은 요구·제약에 없는 요소를 임의로 만들지 않는다. (↔ C-3)
- **원칙 3 — 근거 없는 변경·삭제 금지.** 고도화(수정)는 근거(대화·피드백) 없이는 발생하지 않는다. (↔ C-4)
- **원칙 4 — 근거 없는 휘발 금지.** 대화에 등장한 요청은 채택되거나 명시적으로 제외되어야 하며, 아무 반영처 없이 사라지지 않는다. (↔ C-5)
- **원칙 5 — 계약 추출의 결정성.** export 시점의 시각 계약 추출은 언어 모델을 쓰지 않는다. 동일 입력은 언제나 동일 계약을 낳고, 이 단계의 모델 비용은 0이다. (↔ C-1)
- **원칙 6 — 근거 보존.** 모든 산출물은 자신이 파생된 상위 산출물과 그 근거(회의 발언)를 함께 보존한다.

## 2. 핵심 개념

### 2.1 두 층위 — 앱 자체 vs 앱이 생성하는 대상물

이 제품에는 requirements·constraints·목업이 **두 겹**으로 존재한다. 문서와 구현은 이 둘을 절대 뒤섞지 않는다.

| 층위 | 대상 | 예 |
|---|---|---|
| **(a) 앱 자체** | Blueprint Agent 콘솔의 요구·제약·UI | 이 문서 §3의 기능, 콘솔 화면 |
| **(b) 생성 대상물** | 앱이 사용자를 도와 만들어내는 대상 제품의 요구·제약·목업 | 사용자의 "태스크 상세 화면" 요구·제약과 그 목업 |

- **시각 계약 추출**은 (b) 생성 대상물의 목업에만 적용된다. (a) 앱 자체에는 해당 없음.
- **`samsung-design-guidelines.md`** 는 (a) 콘솔과 (b) 생성 목업 **양쪽 모두**에 적용된다.

### 2.2 개념 구조 — 프로젝트 > 회의체 > 버전

```
프로젝트 (상위 계층, 영속)
 └─ 회의체 (하나의 토론 단위; 여러 번 이터레이션)
     └─ 버전 (한 회의체 안의 피드백 루프마다 생성)
```

- 한 프로젝트는 여러 **회의체**를 가질 수 있다. 각 회의체는 그 안에서 정해진 요구에 따라 독립적으로 돈다.
- 한 회의체는 피드백 루프를 돌며 **여러 버전**을 만든다.
- **필수(required)**: freeze된 major 버전과 중요 의결사항은 **프로젝트 층위에서 되짚어볼 수 있게 영속**한다.
- **허용(optional simplification)**: freeze되지 않은 버전은 회의체 종결 시 휘발되어도 무방하다. 휘발은 요구 기능이 아니라 **허용되는 단순화**이며, 이를 위한 별도 생명주기 장치를 만들 의무는 없다(C-6).

### 2.3 처리·모델 사용 요약표

| 단계 | 입력 | 출력 | 모델 | 실행 |
|---|---|---|---|---|
| 대화 입력·저장 | 텍스트/음성 발화 | 저장된 대화(발언 단위) | 미사용 | 동기 |
| req·constraints 추출 | 대화 | requirements·constraints(근거 태그) | **사용** | 비동기 |
| 목업 publish | req·constraints | HTML 목업 | **사용** | 비동기 |
| 고도화(델타 수정) | 직전 버전 + 근거 델타 | 새 버전 req·constraints·목업 | **사용** | 비동기 |
| 커버리지/누락 체크 | 대화 + 현재 req·constraints | 누락 후보 목록 | **사용** | 비동기 |
| freeze | 현재 버전 | major 버전 고정 | 미사용 | 동기 |
| 시각 계약 추출 | 목업(렌더 결과) | 시각 계약 | **미사용(결정적)** | 동기 |
| export | 확정본·목업·추적 메타·계약 | export 산출물 | 미사용 | 동기 |

> 모델을 쓰는 단계는 비동기로 즉시 작업 식별자를 반환하고 상태를 조회·스트리밍한다. 결정적 단계(freeze·계약 추출·export)는 동기로 즉시 응답한다.

## 3. 핵심 기능 (CORE)

### 3.1 대화 입력·저장

**목적**: 회의 발언을 시스템의 최초 입력으로 확보한다.

- **텍스트 입력이 메인 시나리오다.** `발언자: 내용` 형식을 수용하고, 발언자 라벨이 없는 줄도 하나의 발언으로 받는다.
- 발언을 **채팅 버블**로 시간순 표시하고, 발언자별로 시각 구분한다.
- 작업 중 발언을 추가하면 이후 처리에 반영된다.
- **음성 입력은 얇은 어댑터**로만 제공한다(§4, C-6). 마이크 발화 → 텍스트 전사 → 텍스트 입력과 동일 경로에 투입. 고수준 설계 대상이 아니다.

### 3.2 requirements·constraints 추출

**목적**: 비정형 대화를, 후속 단계가 소비할 수 있는 **requirements와 constraints로 대칭적으로** 정리한다.

- **requirements**와 **constraints**는 동급 1급 산출물이다. 둘 다 대화에서 추출되고, 근거·버전·freeze·export의 라이프사이클을 똑같이 탄다.
  - **requirements**: 화면 목적, 데이터 객체·필드, 사용자 액션 등 "무엇을 만드나".
  - **constraints**: "이번 범위 밖", "하지 않는 것", 결정된 제약 등 "무엇을 만들지 않나". 특히 §3.5의 "명시적 제외" 결정이 여기로 흘러든다.
- 각 항목은 근거가 된 발언을 `[근거: u-002, u-005]` 형태로 태그한다.
- **대화에 명시되지 않은 내용을 추가하지 않는다(원칙 2 / C-3).** 부족한 것은 채우지 말고 부족한 채로 두어 다음 발언으로 들어오게 한다.
- 사람이 읽을 수 있는 문서 형태를 유지하여, 후속 단계와 화면 표시에 동일 형태로 전달된다.

### 3.3 목업 publish

**목적**: 정리된 requirements·constraints를 이해관계자가 즉시 볼 수 있는 화면으로 전환한다.

- requirements·constraints로부터 **단일 HTML 목업**을 생성한다.
- 요구·제약에 명시된 요소만 생성하며, 명시되지 않은 요소를 임의로 추가하지 않는다(원칙 2 / C-3).
- 시각 규격(색·타이포·컴포넌트·간격·반경)은 `samsung-design-guidelines.md`를 따른다(층위 b, §2.1).
- 콘솔 내에서 즉시 프리뷰하며, 생성 진행 상태를 실시간 표시한다.

### 3.4 피드백 이터레이션·고도화

**목적**: 목업을 본 사람들의 피드백을 반영하여 requirements·constraints를 develop하고, 목업을 republish한다.

- 피드백은 **대화·요청으로 들어와 requirements·constraints를 고친다**(목업 직접 편집이 아니다, 원칙 1).
- 수정은 **근거 기반 델타**로 한정한다: 직전 버전 + 근거가 된 델타 발언/요청에서 도출된 수정분만 반영한다. **근거 없이는 수정이 발생하지 않는다(원칙 3 / C-4).**
- 수정 결과는 새 버전으로 기록하며, 생성 모드(신규/수정)와 부모 버전을 함께 남긴다.
- 고도화 후 목업을 republish하여 다시 확인 루프로 돌아간다.

### 3.5 커버리지/누락 체크

**목적**: 대화에서 요청·언급됐으나 requirements·constraints에 반영되지 않은 항목을, 오해가 개발까지 새어나가기 전에 회의 자리에서 잡는다.

- 모델이 **대화 전체 vs 현재 requirements·constraints 집합**을 대조하여 "요청됐으나 반영 안 된 항목" 목록(누락 후보)을 뽑는다.
- **자동으로 추가하지 않는다.** 사람에게 체크리스트로 제시(flag)하고, **휴먼 게이트가 각 항목을 다음 중 하나로 명시적으로 처리**한다:
  - **채택** → requirement 또는 constraint로 편입(근거 대화가 이미 있으므로 추적성 자동 충족)
  - **의도적 제외** → 이 제외 결정 자체가 하나의 **constraint**가 된다(예: "첨부파일은 이번 버전 범위 밖 — 근거: u-004")
- 대화에 등장한 요청은 채택 또는 명시적 제외 중 하나로 귀결되며, **아무 반영처 없이 휘발되지 않는다(원칙 4 / C-5).**

### 3.6 버전·freeze

**목적**: 사람의 검토가 만족에 도달한 시점을 명시적 경계로 고정한다.

- 사용자가 특정 버전을 **freeze**하면 **major 버전**으로 기록한다.
- major 버전과 중요 의결사항은 프로젝트 층위에서 되짚어볼 수 있게 영속한다(§2.2).
- 버전마다 보존하는 항목:
  - 생성 시각 / 생성 모드(신규·수정) / 부모 버전
  - 해당 시점의 대화 스냅샷
  - 이 버전의 근거 발언 목록(신규=전체, 수정=델타)
  - requirements·constraints 요약
  - 모델 사용량(입력·출력 토큰)

### 3.7 export & re-import

#### 3.7.1 export 내용물

freeze된 major 버전을 export한다. export 산출물에는 다음이 담긴다:

- requirements·constraints 확정본
- 목업
- 근거-대화 추적 메타(각 항목이 어떤 발언에서 나왔는가)

#### 3.7.2 시각 계약 추출 (export 시점, 결정적)

**목적**: HTML 목업은 특정 케이스(예: 대량 더미 데이터가 들어간 화면)에서 태그가 불필요하게 과생산될 수 있다. 하류의 다른 개발 사이클·AI 세션이 매번 HTML 전문을 읽으면 입력 비용이 크고 오독 위험이 있다. 이를 막기 위해 export 시점에 목업에서 **시각 계약**만 추출하여 하류로 전파한다.

- **언어 모델을 쓰지 않고 결정적으로** 추출한다(원칙 5 / C-1). 렌더 기반(헤드리스 브라우저 등 — 도구는 자유). 동일 입력은 언제나 동일 계약을 낳는다.
- 계약은 사람이 읽고 기계가 파싱할 수 있는 구조화 형식이다.
- 이 결정성이 하류의 저비용·오독 없는 전파를 보장하는, 이 제품의 핵심 차별점이다.

#### 3.7.3 export의 두 목적과 왕복(round-trip)

- **목적 (a) — 재import**: 다음·다른 회의체에서 import하여 논의를 이어간다. **이 앱이 낸 export를 이 앱이 다시 읽을 수 있어야 한다(왕복 보장).** 재import에 전체 대화가 필요하지는 않으나, **중요 의결사항과 그 근거는 반드시 포함**되어야 한다.
- **목적 (b) — 하류 개발 투입**: export 산출물을 다른 개발 사이클(사람이든 AI든, 꼭 AI-DLC가 아니어도)의 입력으로 태운다. 하류가 SRS·HLD·LLD·ADR 등을 작성할 때 **정보 재수집 없이 이어질 수 있도록** 하는 것이 export의 의의다.

### 3.8 근거 추적성

**목적**: 모든 요구·제약의 출처를 회의 발언으로 환원한다.

- 각 requirement/constraint 항목은 근거가 된 발언까지 역추적 가능하다.
- 시스템은 다음 질문에 산출물만으로 답할 수 있어야 한다:

| 질문 | 답을 주는 근거 |
|---|---|
| 언제 이 요구가 들어왔는가 | 버전 생성 시각 + freeze 타임스탬프 |
| 누가 요청했는가 | 버전별 대화 스냅샷의 발언자 라벨 |
| 무엇이 바뀌었는가 | 직전 스냅샷 대비 델타 발언 + 생성 모드 + 부모 버전 |
| 왜 바뀌었는가 | 델타 발언 → 수정 → 반영 결과의 연결 |
| 요청이 누락되지 않았는가 | §3.5 커버리지 체크 + 채택/제외 결정 기록 |

### 3.9 작업 콘솔

**목적**: 회의에 함께 앉은 사람들이 하나의 화면에서 골든패스를 돈다.

- **단일 통합 콘솔이다. 이해관계자 모드/개발자 모드 같은 분리는 두지 않는다.**
- 좌측: 회의 대화를 채팅 형태로 표시하고 발언 추가.
- 우측: 산출물(requirements·constraints 문서 / 목업 프리뷰) 열람.
- **실행 상태 관리**:
  - 모델을 쓰는 처리는 비동기로 진행 상태를 실시간 표시·스트리밍한다.
  - 결정적 처리(freeze·계약 추출·export)는 동기로 즉시 응답한다.
  - **실패 시 오류 사유를 표시하고 이전 상태를 보존한다.**
- **사용자 흐름 피드백**: 빈 화면(데이터 없음), 로딩, 성공, 오류 상태를 각각 명확히 보여준다.

## 4. 부수 기능 (Non-core)

핵심 골든패스에 종속되며, core를 복잡하게 만들지 않는 선에서만 존재한다(C-6).

- **음성 입력 (kick 아이템)**: 텍스트 입력창 앞에 붙는 얇은 어댑터. 마이크 발화 → STT 전사 → 텍스트로 대화에 추가. "동작만 하면 됨" 수준이며, 고수준 설계·무거운 로컬 처리 제약을 두지 않는다. 저장 대상은 원음이 아니라 전사 텍스트이고, STT 키는 코드에 하드코딩하지 않는다(env). 마이크 접근은 사용자가 명시적으로 개시한다.
- 그 외 편의 요소는 골든패스 완결성을 해치지 않는 범위에서만 추가한다.

## 6. 인수·완료 정의 (Acceptance / DoD)

각 기능은 "동작한다"를 다음 기준으로 판정한다. (대회 평가기준을 기능별 완료 정의로 번역한 것이다.)

- **골든패스 실증 앵커 ★**: 대화 → requirements·constraints → 목업 → 이터레이션 → freeze → export의 **한 시나리오가 end-to-end로 실제 동작하고, 그 화면을 담은 시연 스크린샷이 `screenshots/` 또는 `result/`에 존재**한다. 이 하나만은 반드시 성립해야 한다.
- **빌드·실행 가능성**: 의존성 선언·진입점·락파일이 갖춰져, 처음 보는 사람이 설치·실행까지 막히지 않는다.
- **사용성**: 콘솔 화면만 보고 다음 행동을 알 수 있고, 빈 화면·로딩·성공·오류 피드백이 각 경로에 존재한다(§3.9).
- **흐름 완결성**: 진입점부터 export까지 호출이 실제 구현에 닿는다. 핵심 경로에 TODO·빈 함수·스텁을 남기지 않는다.
- **추적성 증거**: §3.8의 질문들에 산출물만으로 답할 수 있다 — AI-DLC 활용도의 증거.
- **유지보수성·보안**: 시크릿은 env로 분리(코드 하드코딩 금지), 주요 경로에 입력 검증과 오류 처리가 있다.

## 부록

### A. 용어 정의

- **requirements / constraints**: 대화에서 대칭적으로 추출되는 동급 1급 산출물. 전자는 "무엇을 만드나", 후자는 "무엇을 만들지 않나".
- **목업(Mockup)**: requirements·constraints로부터 생성되는 파생 HTML 화면. 사람의 눈 확인용 매개체.
- **회의체**: 하나의 토론 단위. 여러 피드백 루프(버전)를 품는다.
- **버전 / major 버전**: 피드백 루프마다 생기는 산출물 스냅샷. freeze된 것이 major.
- **freeze**: 검토 만족 시점을 major 버전으로 고정하는 행위.
- **시각 계약(Visual Contract)**: export 시점에 목업에서 결정적으로 추출한 기계 판독 문서. 하류 전파의 저비용 매개체.
- **고도화(Develop)**: 근거 기반 델타로 requirements·constraints를 개선하는 것.
- **커버리지/누락 체크**: 대화 대비 현재 요구·제약의 누락을 flag하는 기능.
- **근거 사슬**: 회의 발언에서 시작해 각 산출물이 상위 근거를 보존하는 파생 관계.

### B. 상충 시 우선순위

기능 요구가 §1.4 불변 원칙과 상충하면 **불변 원칙이 우선한다.** 특히 다음을 타협하지 않는다:
1. 계약 추출 단계에 모델을 도입하여 결정성을 훼손하는 설계 (원칙 5 / C-1)
2. 목업을 원천으로 삼아 requirements·constraints를 우회 수정하는 설계 (원칙 1 / C-2)
3. 근거 없는 보완 생성·근거 없는 휘발을 허용하는 설계 (원칙 2·4 / C-3·C-5)

### D. 구현 참고 (요구 아님 — 이전 사이클의 실전 지식)

아래는 요구사항이 아니라, 참고용 구현 힌트다. 지킬 의무는 없고, 도움이 되면 쓴다.

- **처리 모델**: 모델 쓰는 엔드포인트는 비동기(작업 식별자 반환 → 상태 폴링/스트리밍), 결정적 엔드포인트(freeze·계약 추출)는 동기.
- **음성 얇은 경로**: 오디오 청크 업로드 → 서버 전사 → 대화에 `발언자: 내용` 라인 추가(스트리밍).
- **알려진 함정(gotchas)**:
  - `crypto.randomUUID`는 보안 컨텍스트(HTTPS/localhost)에만 존재 — LAN http 접속 시 없어 크래시. 폴백 필수.
  - 대화 파싱은 `발언자: 내용`에서 발언자 라벨(짧은 접두)만 매칭, 아니면 순수 텍스트로 취급.
  - 진행 중(busy) 상태 해제는 스트리밍 이벤트가 아니라 호출부 finally가 담당(체인 중 버튼 풀림 방지).
  - 목업을 iframe으로 프리뷰하면, 같은-오리진일 때 로드 시 단축키 핸들러를 iframe 문서에도 주입(iframe이 키 입력을 삼키는 것 방지).
