# Blueprint Agent 요구사항 정의서

## 1. 프로젝트 개요

### 1.1 서비스 비전

회의에서 오간 말과 이미 존재하는 화면을, 사람이 눈으로 확인하고 확정하는 순간에 기계가 저비용으로 이해할 수 있는 계약(contract)으로 변환하여, 요구사항 명세 · 데이터 모델 · API 명세 · 실행 코드까지 근거를 잃지 않고 도출하는 **Requirement-to-Architecture 시스템**

### 1.2 해결하려는 문제

**문제 1 — 요구사항 오해로 인한 재작업**
소프트웨어 개발에서 가장 비싼 재작업은 "만들고 나서야 요구가 잘못 이해됐음을 발견하는 것"이다. 텍스트 요구사항은 이해관계자마다 다르게 읽히며, 그 차이는 구현이 끝난 뒤에야 드러난다.

**문제 2 — 사람용 산출물을 기계가 읽는 비용**
화면 목업은 *사람의 검토*를 위해 만들어진 산출물이다. 이것을 후속 자동화 단계가 원본 그대로 읽으면 입력 비용이 크고, 시각적 잡음이 판단 품질을 떨어뜨린다.

**문제 3 — 근거를 잃은 변경**
자동화된 도구가 산출물을 수정할 때 "왜 이렇게 바뀌었는가"에 답할 수 없으면, 변경을 검증할 방법이 없다. 요구의 출처가 소실되는 순간 결과물은 감사 불가능해진다.

### 1.3 핵심 가치 제안

**기획자 · 이해관계자 관점**
- 회의 중 나온 말이 즉시 눈으로 볼 수 있는 화면이 되어, 오해를 회의 자리에서 발견
- 화면을 보며 대화로 수정하고, 만족한 시점에 "확정"을 선언하는 것만으로 후속 명세가 도출됨
- 전문 문서 작성 능력 없이도 정식 요구사항 명세를 산출

**개발자 관점**
- 확정된 화면과 1:1로 대응하는 기계 판독 계약을 받으므로, 화면 해석에 대한 추측이 불필요
- 모든 요구사항 항목이 원래 발언까지 역추적 가능
- 이미 운영 중인 레거시 화면도 같은 표현 체계로 흡수되어, 신규·기존이 하나의 파이프라인에서 다뤄짐

**조직 관점**
- 자동화 단계의 입력 비용을 정량적으로 측정·증명 가능
- 요구 → 화면 → 계약 → 명세 → 코드의 전 구간에 근거 사슬이 남아 감사 가능

**시장 차별화**
- 화면 생성 도구가 아니라, **화면을 매개체로 쓰는 요구사항-아키텍처 도출 시스템**
- 신규 개발(그린필드)과 레거시 흡수(브라운필드)를 동일한 중간 표현으로 통합

### 1.4 시스템 불변 원칙

아래 원칙은 전 기능에 우선하며, 어떤 기능도 이를 위반해서는 안 된다.

**원칙 1 — 원본 화면 마크업 격리**
언어 모델은 화면 마크업 원본을 소비하지 않는다. 원본은 정해진 변환 지점에서 단 한 번만 접촉되고, 이후 모든 단계는 정규화된 중간 표현만 입력으로 받는다. 유일한 예외는 비용 절감을 증명하기 위한 비교 실험의 대조군이다.

**원칙 2 — 확정 단계의 결정성**
화면을 계약으로 변환하는 단계는 언어 모델을 사용하지 않는다. 동일 입력은 언제나 동일 출력을 낳아야 하며, 이 단계의 모델 호출 비용은 0이어야 한다.

**원칙 3 — 근거 없는 생성 금지**
요구 브리프는 입력된 발언에 명시되지 않은 내용을 추가하지 않는다. 화면은 브리프에 명시되지 않은 요소를 임의로 생성하지 않는다. 추측에 의한 보완은 금지한다.

**원칙 4 — 근거 보존**
모든 산출물은 자신이 파생된 상위 산출물과 그 근거(발언 또는 레거시 화면)를 식별 가능한 형태로 함께 보존한다.

## 2. 서비스 구성

### 2.1 주요 구성 요소

- **작업 콘솔**: 이해관계자와 개발자가 사용하는 단일 화면. 회의 대화 입력, 화면 미리보기, 산출물 열람, 단계별 실행을 담당
- **파이프라인 처리 계층**: 요구 캡처 → 화면 공동 설계 → 확정 및 계약 추출 → 명세 역도출 → 코드 생성의 순차 처리
- **레거시 흡수 계층**: 기존 화면 및 기존 사이트를 파이프라인의 중간 표현으로 역산하는 입력 경로
- **산출물 저장소**: 프로젝트별 화면 버전 이력, 확정 시점의 계약, 도출된 명세, 근거 메타데이터를 영속 보관
- **측정 계층**: 입력 비용 절감과 품질 동등성을 실측하는 비교 실험 실행기

### 2.2 처리 계층 정의

| 계층 | 입력 | 출력 | 모델 사용 |
|---|---|---|---|
| 요구 캡처 | 회의 녹취 텍스트 | 구조화된 요구 브리프 | 사용 |
| 화면 공동 설계 | 요구 브리프 | 의도 메타데이터가 부착된 단일 화면 | 사용 |
| 레거시 흡수 | 기존 화면(주소·마크업·이미지·소스) | 정규화된 화면 모델 → 초기 버전 | 입력 종류에 따라 0~1회 |
| 확정 및 계약 추출 | 확정된 화면 | 시각 계약 문서 | **미사용 (결정적)** |
| 명세 역도출 | 시각 계약 문서 | 요구사항 명세 · 데이터 모델 · API 명세 | 사용 |
| 코드 생성 | 도출된 명세 | 프론트엔드 · 백엔드 · 데이터베이스 코드 | 사용 |

## 3. 핵심 기능 요구사항

### 3.1 요구 캡처 기능

#### 3.1.1 회의 녹취 입력

**목적**: 회의에서 오간 발언을 시스템의 최초 입력으로 확보

**기능 요구사항**:
- 발언자 라벨이 붙은 텍스트 형식(`발언자: 내용`)의 녹취 입력
- 발언자 라벨이 없는 줄도 하나의 발언으로 수용
- 예시 녹취 템플릿 목록 제공 및 선택 시 즉시 로드
- 작업 중 발언을 추가하면 이후 처리에 반영

**UI/UX 요구사항**:
- 발언을 채팅 버블 형태로 시간순 표시
- 발언자별 시각적 구분

**데이터 관리**:
- 녹취 원문은 각 화면 버전 생성 시점의 스냅샷으로 보존

#### 3.1.2 실시간 음성 인식 (선택 기능)

**목적**: 회의 음성을 별도 전사 작업 없이 직접 입력으로 전환

**기능 요구사항**:
- 마이크 입력을 실시간으로 텍스트화하여 녹취에 반영
- 화자 분리를 수행하여 발언자 라벨을 자동 부여
- 한국어를 포함한 다국어 인식
- 발화 후 텍스트 반영까지 수 초 이내

**제약 요구사항**:
- 음성 데이터가 외부 서비스로 전송되지 않는 로컬 처리 방식이어야 한다
- 음성 인식 자원은 최초 1회 준비 절차로 설치하며, 미설치 시 이 기능만 비활성화되고 나머지 기능은 정상 동작해야 한다

#### 3.1.3 발언 식별 체계

**목적**: 개별 발언을 안정적으로 참조할 수 있는 식별자 부여

**기능 요구사항**:
- 각 발언에 문서 순서 기반의 식별자(`u-001` 형식)를 결정적으로 부여
- 동일한 녹취에 대해서는 언제나 동일한 식별자가 부여되어야 한다 (버전 간 식별자 안정성)
- 발언 추가 시 기존 발언의 식별자는 변경되지 않는다

**데이터 관리**:
- 식별자 부여는 모델 호출 없이 결정적으로 수행

#### 3.1.4 요구 브리프 추출

**목적**: 비정형 발언을 후속 단계가 소비할 수 있는 구조화된 요구 명세로 변환

**기능 요구사항**:
- 다음 세 영역으로 구조화된 브리프 산출
  - 화면 목적
  - 데이터 객체와 필드 (필드별 타입 및 표현 형태 포함)
  - 사용자 액션 (액션명, 대상 객체, 변경 필드, 결과값)
- 녹취에 명시되지 않은 내용은 추가하지 않는다 (§1.4 원칙 3)
- 브리프의 각 항목은 근거가 된 발언 식별자를 `[근거: u-002, u-005]` 형태로 태그한다
- 브리프는 사람이 읽을 수 있는 문서 형태를 유지하여, 후속 단계와 화면 표시에 동일한 형태로 전달된다

**처리 방식 요구사항**:
- 장시간 소요 가능한 작업이므로 비동기 실행 후 진행 상태를 조회할 수 있어야 한다

### 3.2 화면 공동 설계 기능

#### 3.2.1 화면 생성

**목적**: 요구 브리프를 이해관계자가 즉시 볼 수 있는 화면으로 전환

**기능 요구사항**:
- 요구 브리프로부터 단일 화면 산출물 생성
- 브리프에 명시된 요소만 생성하며, 명시되지 않은 요소를 임의로 추가하지 않는다 (§1.4 원칙 3)
- 생성된 화면의 모든 의미 요소에 **저자 의도 메타데이터**를 부착한다
  - 컴포넌트 식별자 및 역할 구분 (제목 / 배지 / 버튼 / 입력 등)
  - 데이터 바인딩 (어떤 객체의 어떤 필드를 표시하는가)
  - 액션 정의 (동사, 대상 객체, 변경 필드, 결과값)
- 메타데이터는 화면의 시각적 표현이 담을 수 없는 *의도*를 기계 판독 가능한 형태로 보존하기 위한 것이며, 후속 확정 단계의 필수 입력이다

**UI/UX 요구사항**:
- 생성된 화면을 콘솔 내에서 즉시 미리보기
- 미리보기를 지정 해상도 기준 등비 스케일 전체화면으로 확대 가능
- 생성 진행 상태를 실시간 표시

#### 3.2.2 대화 기반 델타 수정

**목적**: 화면 전체를 재생성하지 않고, 추가된 발언만 반영하여 수정

**기능 요구사항**:
- 직전 버전 생성 시점의 대화 스냅샷 이후 **추가된 발언만** 델타로 추출
- 수정 시 입력은 **직전 버전 화면 + 델타 발언에서 도출된 수정 브리프**로 한정한다
- 근거가 되는 발언 없이는 수정이 발생할 수 없는 구조여야 한다
- 수정 결과는 새 버전으로 기록하며, 생성 모드(신규/수정)와 부모 버전을 함께 남긴다

**UI/UX 요구사항**:
- 수정 모드로 동작 중임을 시각적으로 구분 표시

#### 3.2.3 버전 이력 관리

**목적**: 화면의 변천 과정과 그 근거를 언제든 검증 가능하게 보존

**기능 요구사항**:
- 프로젝트별 · 버전별 화면 산출물 영속화
- 버전 목록 조회 및 과거 버전 재로드·미리보기
- 버전 간 비교를 위한 메타데이터 제공

**데이터 관리** (버전마다 보존해야 하는 항목):
- 생성 시각
- 생성 모드 (신규 생성 / 수정)
- 부모 버전 식별자
- 해당 시점의 대화 스냅샷 전문
- 이 버전의 근거 발언 목록 (신규 생성 = 전체 발언, 수정 = 델타 발언만)
- 요구 브리프 요약
- 모델 사용량 (입력·출력 토큰)
- 출처 구분 (회의 발언 기반 / 레거시 흡수 기반)

### 3.3 확정 및 계약 추출 기능

#### 3.3.1 시각적 확정 (Freeze)

**목적**: 사람의 검토가 끝난 시점을 명시적 경계로 삼아, 이후 자동화의 기준점을 고정

**기능 요구사항**:
- 사용자가 특정 화면 버전에 대해 "확정"을 선언
- 확정 시점의 타임스탬프와 함께 산출물 일체를 별도 실행 단위로 보존
- 확정 이후의 후속 단계는 확정된 계약만을 입력으로 삼는다

#### 3.3.2 시각 계약 추출

**목적**: 확정된 화면을 기계가 저비용으로 이해하는 계약 문서로 변환

**기능 요구사항**:
- **언어 모델을 사용하지 않고** 결정적으로 추출한다 (§1.4 원칙 2)
- 세 가지 정보원을 융합하여 추출
  - 기하 정보: 렌더링 결과에서 계산된 위치·크기·스타일
  - 구조 정보: 문서 구조에서 도출된 요소 역할
  - 의도 정보: §3.2.1에서 부착된 저자 의도 메타데이터
- 계약 문서는 사람이 읽을 수 있고 기계가 파싱할 수 있는 구조화 형식이어야 한다

**계약 문서 필수 구성**:
- 페이지 정보 (제목, 기준 뷰포트 크기)
- 데이터 객체 목록 (객체 식별자, 필드명, 타입, 표현 형태)
- 컴포넌트 목록 (식별자, 역할, 경계 상자, 데이터 바인딩)
- 액션 목록 (식별자, 역할, 라벨, 경계 상자, 트리거 시 동작 정의)
- 상태 흐름 (어떤 액션이 어떤 상태 전이를 유발하는가)

**성능 요구사항**:
- 이 단계는 동기 처리로 즉시 응답 가능해야 한다
- 모델 호출 비용 0

---

### 3.4 명세 역도출 기능

#### 3.4.1 명세 도출

**목적**: 시각 계약 하나로부터 개발에 필요한 세 종류의 정식 명세를 도출

**기능 요구사항**:
- **입력은 시각 계약 문서로 한정한다.** 원본 화면 마크업이나 녹취 원문을 입력으로 받지 않는다 (§1.4 원칙 1)
- 다음 세 산출물을 도출
  - **요구사항 명세(SRS)**: 계약의 액션과 상태 흐름에서 도출
  - **데이터 모델(ERD)**: 계약의 데이터 객체와 참조 관계에서 도출
  - **API 명세(OpenAPI)**: 계약 액션의 동사와 대상에서 도출
- 요구사항 명세의 기능 요구사항 항목은 `FR-01` 형식의 체계적 번호를 부여하여, 명세 간 상호 참조가 가능해야 한다

**UI/UX 요구사항**:
- 도출된 명세를 표와 코드 블록을 포함한 서식 문서로 렌더링하여 콘솔에서 열람 가능

**처리 방식 요구사항**:
- 비동기 실행 후 진행 상태 조회

---

### 3.5 코드 생성 기능

**목적**: 도출된 명세가 실제 실행 가능한 코드로 이어짐을 실증

**기능 요구사항**:
- 도출된 명세로부터 3계층 코드 산출
  - 프론트엔드 화면 컴포넌트
  - 백엔드 라우트 (API 명세의 경로·동사 준수)
  - 데이터베이스 스키마 정의
- 생성된 코드는 근거가 된 요구사항 항목 번호를 주석으로 참조하여, 코드에서 명세로 역추적이 가능해야 한다

**범위 요구사항**:
- 실행 가능한 완전한 애플리케이션이 아니라, 명세 → 코드 연결의 실증을 목적으로 하는 대표 파일 집합을 산출한다

### 3.6 레거시 흡수 기능

#### 3.6.1 단일 화면 흡수

**목적**: 이미 운영 중인 화면을 신규 개발과 동일한 표현 체계로 역산

**기능 요구사항**:
- 네 가지 입력 종류를 지원
  | 입력 종류 | 처리 방식 | 모델 호출 |
  |---|---|---|
  | 화면 주소(URL) | 실제 렌더링 결과의 결정적 해석 | 0회 |
  | 마크업 파일 | 결정적 해석 | 0회 |
  | 화면 캡처 이미지 | 시각 인식 | 1회 |
  | 화면 소스코드 | 소스 해석 | 1회 |
- 입력 종류와 무관하게 **공통 중간 표현(화면 모델)** 으로 정규화한다
- 원본은 흡수 단계 내부에서 단 한 번만 접촉되며, 이후 모든 처리는 정규화된 화면 모델만 사용한다 (§1.4 원칙 1)
- 정규화 결과는 해당 프로젝트의 **초기 버전(v0)** 으로 등록되며, 출처가 레거시임을 명시한다

**충실도 요구사항** (하이브리드 충실도):
- **구조**: 화면 모델에 기반한 사실 재현 — 추측하지 않는다
- **톤**: 렌더링 결과에서 결정적으로 추출한 디자인 토큰(색·간격·서체 등)을 주입
- **픽셀**: 픽셀 단위 재현은 목표로 하지 않는다

**데이터 관리**:
- 화면 모델 스냅샷을 영속화하여, 생성된 화면의 각 요소가 원본의 어느 요소에서 왔는지 역추적 가능해야 한다
- 원본 출처(주소 또는 파일)와 캡처 시각을 기록

#### 3.6.2 사이트 전체 흡수

**목적**: 화면 단위를 넘어 기존 서비스 전체를 흡수

**기능 요구사항**:
- 시작 주소에서 동일 사이트 내 링크를 탐색하여 페이지 목록을 발견
- 사이트맵이 존재하는 경우 이를 함께 활용
- 발견된 각 페이지를 개별 초기 버전으로 분해
- 분해는 순차적으로 수행하며, 대상 서버에 부하를 주지 않도록 요청 간 지연을 둔다
- **네비게이션 그래프**: 페이지 간 이동 관계(출발 페이지, 도착 페이지, 링크 텍스트)를 결정적으로 수집
- **병합 데이터 모델**: 페이지별 데이터 객체를 사이트 전체 관점에서 병합한 통합 모델을 결정적으로 산출 (모델 호출 0회)
- 사이트 흡수 후 명세 도출 시, 개별 페이지 계약들을 하나의 **앱 단위 합성 계약**으로 묶어 서비스 전체의 요구사항 명세 · 데이터 모델 · API 명세를 도출한다
- 네비게이션 그래프는 합성 계약의 상태 흐름으로 반영된다

**데이터 관리**:
- 프로젝트별 앱 이력(페이지 목록, 네비게이션 엣지, 병합 데이터 객체)을 영속화

#### 3.6.3 크롤 실행 제어

**목적**: 불필요한 페이지 분해에 드는 비용을 사용자가 통제

**기능 요구사항**:
- **탐색 전용 모드**: 페이지 발견만 수행하고 분해는 하지 않는다. 모델 호출 0회, 동기 응답으로 발견된 페이지 목록(주소·제목)을 즉시 반환
- **선택 분해**: 사용자가 선택한 페이지만 분해한다. 네비게이션 엣지 수집을 위한 탐색은 전체에 대해 수행하되, 분해 대상만 제한
- **재가동 스킵**: 이미 흡수한 이력이 있는 페이지는 분해를 건너뛰고 기존 버전을 재사용한다. 기존 버전 번호를 유지하며 새 버전을 만들지 않는다
- 최대 페이지 수 상한을 지정 가능

**UI/UX 요구사항**:
- 2단계 흐름으로 제공
  1. "페이지 찾기" → 발견된 페이지를 체크리스트로 표시 (전체 선택 지원, 기본값 전체 선택)
  2. "분해해서 가져오기" → 선택된 페이지만 실행. "이미 가져온 페이지 건너뛰기" 옵션 기본 활성화
- 진행 상황을 `N/M 페이지 분해 중` 형태로 표시

#### 3.6.4 흡수 이후의 두 경로

**목적**: 흡수된 레거시가 신규 개발 흐름에 합류

**기능 요구사항**:
- **경로 1 — 부분 수정**: 초기 버전에 대해 §3.2.2의 발언 델타 수정을 적용하여 점진 개선. 이후 버전부터는 신규 개발과 동일한 근거 사슬에 합류
- **경로 2 — 완전 재설계**: 초기 버전을 즉시 확정하여 현행(as-is) 명세를 도출하고, 이를 기반으로 재설계(to-be)를 진행

### 3.7 추적성 기능

**목적**: 모든 요구와 변경의 출처를 회의 발언 또는 레거시 화면으로 환원

**기능 요구사항**:
- 다음 두 근거 원천에서 시작하는 추적 사슬을 유지한다
  - **원천 ①** 회의 발언 (누가 · 언제 · 무엇을)
  - **원천 ②** 레거시 화면 (출처 · 캡처 시각)
- 사슬의 각 단계는 상위 산출물과 근거를 함께 보존한다
  ```
  회의 발언 (발언 ID 부여)
   └─ 요구 브리프 (항목별 [근거: u-XXX] 태그)
       └─ 화면 버전 vN (생성 시각·모드·부모 버전·대화 스냅샷·근거 발언 목록)
           └─ 시각 계약 (확정 시점 고정)
               └─ 요구사항 명세(FR-XX) · 데이터 모델 · API 명세
                   └─ 코드 (요구사항 항목 참조 주석)

  레거시 화면 (출처·캡처 시각)
   └─ 화면 모델 스냅샷 (원본 요소와 1:1 역추적)
       └─ 화면 버전 v0 → 이후 위 사슬에 합류
  ```
- 시스템은 다음 질문 각각에 산출물만으로 답할 수 있어야 한다

| 질문 | 답을 주는 근거 |
|---|---|
| 언제 이 요구가 들어왔는가 | 버전 생성 시각 + 확정 타임스탬프 |
| 누가 요청했는가 | 버전별 대화 스냅샷의 발언자 라벨 |
| 무엇이 바뀌었는가 | 직전 스냅샷 대비 델타 발언 + 생성 모드 + 부모 버전 |
| 왜 바뀌었는가 | 델타 발언 → 수정 브리프 → 반영 결과의 연결 |
| 자동화가 수정 시 근거를 보는가 | 수정 모드의 입력이 직전 버전 + 근거 브리프로 구조적으로 한정됨 |
| 과잉 변경을 막는가 | §1.4 원칙 3의 생성 금지 규칙 |

### 3.8 비용 절감 증명 기능

**목적**: 계약 기반 접근이 실제로 입력 비용을 줄이며, 그것이 품질 저하와 교환되지 않음을 실측

**기능 요구사항**:
- 동일한 명세 역도출 작업을 두 조건으로 실행하여 비교
  - (a) 대조군: 원본 화면 마크업을 입력
  - (b) 실험군: 시각 계약 문서를 입력
- 각 조건을 복수 회(3회 이상) 실행하고 **입력 토큰 사용량의 중앙값**을 비교
- 재현성을 위해 생성 무작위성을 제거한 설정으로 실행
- **품질 동등성 검증**: 두 조건의 산출물을 동일 루브릭으로 채점하여 품질 차이를 함께 보고
  - 채점 항목: 데이터 객체 도출 정확도 / 액션 도출 정확도 / API 동사 적합성
  - 항목별 0~3점 척도
- 결과로 절감률과 품질 차이를 함께 제시한다. 절감률만 단독으로 제시하지 않는다

**기록 요구사항**:
- 측정 시점, 사용 모델, 입력 산출물 크기를 결과와 함께 기록한다 (절감률은 모델과 산출물 크기에 따라 달라지므로)

**주석**: 이 기능은 §1.4 원칙 1(원본 마크업 격리)의 **유일한 예외**다. 대조군 실행에 한해 원본 마크업이 모델 입력으로 사용된다.

### 3.9 작업 콘솔 기능

#### 3.9.1 이해관계자 모드 (기본 화면)

**목적**: 전문 지식 없는 사용자가 최소 조작으로 결과에 도달

**기능 요구사항**:
- 단일 실행 버튼으로 다음이 자동 연속 실행
  1. 요구 정리 (요구 브리프 추출)
  2. 화면 생성
  3. 명세 도출
- 좌측: 회의 녹취를 채팅 형태로 표시하고 발언 추가 가능
- 우측: 산출물 전환 토글 (화면 미리보기 / 명세 문서)
- 발언 추가 후 재실행 시 §3.2.2 델타 수정으로 동작

**UI/UX 요구사항**:
- 기본 진입 화면이 이 모드여야 한다
- 단계 진행 상황을 실시간 표시

#### 3.9.2 개발자 모드

**목적**: 파이프라인 각 단계를 개별 실행하고 중간 산출물을 검사

**기능 요구사항**:
- 단계별 개별 실행: 요구 캡처 → 화면 생성 → 확정 → 명세 도출 → 비용 증명 → 코드 생성
- 중간 산출물 검사 탭 제공
  - 요구 브리프
  - 시각 계약 문서
  - 도출 명세
  - 생성 코드
  - 버전 이력
  - 앱 이력 (페이지 목록 · 네비게이션 엣지 · 병합 데이터 객체 · 앱 단위 명세 도출)
- 비용 절감 측정 결과(절감률 · 품질 차이)를 상시 표시

**UI/UX 요구사항**:
- 이해관계자 모드와 개발자 모드를 전환 가능
- 전환 수단은 버튼 · 단축키 · 주소 파라미터의 세 경로 제공

#### 3.9.3 실행 상태 관리

**목적**: 장시간 소요되는 처리 중에도 사용자가 진행을 인지

**기능 요구사항**:
- 모델을 사용하는 모든 처리는 **비동기 실행**으로 즉시 작업 식별자를 반환하고, 상태를 별도 조회 가능해야 한다
- 모델을 사용하지 않는 결정적 처리(확정·계약 추출, 탐색 전용 크롤)는 **동기 처리**로 즉시 응답한다
- 처리 진행 상황을 서버에서 클라이언트로 **실시간 스트리밍**하여 단계별 완료를 즉시 반영한다
- 스트리밍 대상 이벤트: 요구 브리프 / 화면 / 계약 / 명세 / 비용 측정 / 코드
- 실패 시 오류 사유를 사용자에게 표시하고, 이전 상태를 보존한다

## 4. MVP 개발 범위

### 4.1 필수 (핵심 파이프라인)

**목표**: 회의 발언 하나로 명세까지 도달하는 전 구간 실증

- 회의 녹취 입력 및 발언 식별 체계 (§3.1.1, §3.1.3)
- 요구 브리프 추출 — 근거 태그 포함 (§3.1.4)
- 화면 생성 — 의도 메타데이터 부착 (§3.2.1)
- 대화 기반 델타 수정 (§3.2.2)
- 버전 이력 관리 (§3.2.3)
- 시각적 확정 및 계약 추출 — 결정적 (§3.3)
- 명세 역도출 — 요구사항 명세 · 데이터 모델 · API 명세 (§3.4)
- 작업 콘솔 이해관계자 모드 + 개발자 모드 (§3.9)

### 4.2 필수 (차별화 실증)

- 비용 절감 증명 — 절감률 + 품질 동등성 (§3.8)
- 코드 생성 — 명세 → 코드 연결 실증 (§3.5)
- 단일 화면 레거시 흡수 — 4종 입력 (§3.6.1)

### 4.3 필수 (확장 실증)

- 사이트 전체 흡수 및 앱 단위 명세 도출 (§3.6.2)
- 크롤 실행 제어 — 탐색 전용 · 선택 분해 · 재가동 스킵 (§3.6.3)

### 4.4 후순위

- 실시간 음성 인식 (§3.1.2) — 미설치 시 나머지 기능이 정상 동작해야 하므로 독립 배치 가능

## 부록

### A. 용어 정의

- **요구 브리프(Brief)**: 비정형 회의 발언을 화면 목적 · 데이터 객체 · 사용자 액션의 세 영역으로 구조화한 중간 산출물
- **저자 의도 메타데이터**: 생성된 화면의 각 요소에 부착되는 기계 판독용 정보. 컴포넌트 역할, 데이터 바인딩, 액션 정의를 담으며, 픽셀이 표현할 수 없는 *의도*를 보존한다
- **확정(Freeze)**: 사람의 검토가 끝났음을 명시적으로 선언하는 시점. 이 시점 이후의 자동화는 확정된 계약만을 기준으로 삼는다
- **시각 계약(Visual Contract)**: 확정된 화면을 기하 · 구조 · 의도의 세 정보원으로부터 결정적으로 추출한 기계 판독 문서. 후속 명세 도출의 유일한 입력
- **화면 모델(Page Model)**: 레거시 흡수 시 입력 종류(주소·마크업·이미지·소스)와 무관하게 정규화되는 공통 중간 표현
- **디자인 토큰**: 레거시 화면의 렌더링 결과에서 결정적으로 추출한 색·간격·서체 등의 시각 속성. 구조와 분리하여 톤만 이식하는 데 사용
- **하이브리드 충실도**: 구조는 사실 기반으로 재현하고, 톤은 토큰으로 이식하며, 픽셀 재현은 포기하는 레거시 흡수 원칙
- **델타 수정**: 화면 전체를 재생성하지 않고, 직전 버전 생성 시점 이후 추가된 발언만 반영하여 수정하는 방식
- **초기 버전(v0)**: 레거시 흡수 결과로 등록되는 화면 버전. 이후 v1부터 회의 발언 기반 사슬과 합류한다
- **네비게이션 그래프**: 사이트 흡수 시 결정적으로 수집한 페이지 간 이동 관계
- **합성 앱 계약**: 사이트 전체 흡수 후 개별 페이지 계약들을 하나로 묶은 서비스 단위 계약
- **근거 사슬(Traceability Chain)**: 회의 발언 또는 레거시 화면에서 시작하여 코드까지 이어지는, 각 단계가 상위 근거를 보존하는 파생 관계
- **발언 식별자**: 각 발언에 문서 순서 기반으로 부여되는 `u-001` 형식의 안정적 식별자
- **기능 요구사항 번호**: 도출된 요구사항 명세의 각 항목에 부여되는 `FR-01` 형식의 체계적 번호

### B. 상충 시 우선순위

기능 요구사항이 §1.4 시스템 불변 원칙과 상충하는 경우, **불변 원칙이 우선한다.** 특히 다음을 타협해서는 안 된다.

1. 확정·계약 추출 단계에 모델을 도입하여 결정성을 훼손하는 설계
2. 명세 역도출 단계에 원본 화면 마크업을 입력으로 추가하는 설계 (비용 측정의 대조군 제외)
3. 근거 없는 보완 생성을 허용하여 추적 사슬을 끊는 설계
