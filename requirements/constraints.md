## 제외 기능 (구현하지 않음)

### 1. 하류 개발 산출물 — 이 제품의 밖

**이 제품은 requirements·constraints 확정본 + 목업 + 시각 계약까지만 책임진다.** 아래는 export를 소비하는 **하류 개발 사이클(사람이든 AI든)의 몫**이며 이번 범위에서 구현하지 않는다.

- 요구사항 명세(SRS) 산출
- 데이터 모델(ERD) 산출
- API 명세(OpenAPI) 산출
- 설계 문서: 상위 수준 설계(HLD) · 하위 수준 설계(LLD) · 아키텍처 결정 기록(ADR)
- 실행 코드 생성(프론트엔드·백엔드·DB 스키마)
- 코드의 자동 실행·동작 검증, 기존 코드베이스 패치 적용

> 단, **export 시점의 시각 계약 추출은 이 제품의 기능이다**(요구사항 §3.7.2). 계약은 하류가 위 산출물을 저비용·오독 없이 만들도록 돕는 입력일 뿐, 이 제품이 위 산출물을 직접 내지는 않는다.

### 2. 인증 및 계정 관리
- 회원가입·로그인, 조직/팀 멀티테넌시
- 역할 기반 권한(열람/편집/승인 구분), 외부 계정 연동(OAuth·SNS), 다단계 인증

### 3. 화면 편집 및 디자인 도구
- 드래그 앤 드롭 시각 편집기 (목업은 요구·제약에서 생성되는 파생물이지, 손으로 그리는 대상이 아니다 — 원칙 1)
- 픽셀 단위 재현 (기준 뷰포트 1종의 근사 표현만; 픽셀 정합은 목표 아님)
- 디자인 시스템 편집·관리 도구, 컴포넌트 라이브러리 구축
- 반응형 브레이크포인트별 생성(기준 뷰포트 1종만), 다크 모드 등 테마 변형

### 4. 협업 기능
- 다중 사용자 동시 편집
- 산출물 코멘트·리뷰 스레드, 승인 워크플로·결재
- 알림(푸시·이메일·메신저), 변경 이력 구독

### 5. 데이터 및 운영
- **무거운 RDB 서버(Postgres·MySQL 등) 및 별도 DB 인프라.** 단, **서버리스 임베디드 저장(SQLite 등)과 파일 시스템 기반 산출물 저장은 허용한다.** (구조화 인덱스는 임베디드 DB, HTML·export 세트 등 대용량 산출물은 파일 저장을 권장)
- 백업·복구, 보존 기간 정책·자동 삭제
- 사용량 기반 과금·쿼터, 감사 로그 조회 UI(메타데이터 영속화까지만)
- 다중 인스턴스 수평 확장

### 6. 외부 연동
- 이슈 트래커(Jira·Linear), 디자인 도구 임포트/익스포트(Figma)
- 문서 도구(Confluence·Notion), 메신저(Slack·Teams)
- 형상 관리 연동(자동 커밋/PR), 회의 플랫폼 녹취 자동 수집(Zoom·Meet)

> **참고**: export 산출물을 하류가 소비하는 것은 이 제품의 목적이지만, 위 외부 도구와의 **자동 연동**은 범위 밖이다. export는 파일 산출까지만 책임진다.

### 7. 모델 및 인프라
- 모델 파인튜닝, 자체 모델 서빙 인프라
- 다중 모델 라우팅·폴백 정책 UI, 프롬프트 편집 UI(프롬프트는 내부 자산으로 고정)
- 응답 캐싱 계층

### 8. 다국어 및 접근성 자동화
- 콘솔 UI 다국어(한국어 단일), 생성 산출물의 다국어 변형
- 화면 접근성 자동 검사·교정 (단, 디자인 가이드의 대비 4.5:1·focus ring 규칙은 생성 산출물에 적용 — 간소화 대상 아님)

### 9. 음성 입력의 과한 제약 — 두지 않음
음성 입력은 얇은 어댑터다(요구사항 §4, C-6). 아래 무거운 제약은 **의도적으로 두지 않는다**:
- 외부 전송 금지·로컬 전용 처리 강제
- 별도 설치 절차, 화자 분리 고수준 설계

> 이 항목들을 되살리려면 요구사항 §4와 C-6을 함께 개정해야 한다. 얇은 슬라이스 원칙과 정면으로 충돌하기 때문이다.

## 설계 제약 (다르게 만들면 안 되는 것)

아래는 "하지 않는 것"이 아니라 **다르게 만들면 안 되는 것**이다. 요구사항 §1.4 불변 원칙과 1:1 대응한다.

### C-1. export 계약 추출에 언어 모델을 도입하지 않는다
목업을 시각 계약으로 변환하는 단계는 결정적이어야 한다. 렌더 기반(헤드리스 브라우저 등)으로 추출하고, 동일 입력은 언제나 동일 계약을 낳는다. 이 단계의 모델 호출 비용은 0이다. "계약을 더 똑똑하게 만들자"며 모델을 넣는 설계는 저비용·재현성이라는 존재 이유를 무효화하며, 하류의 오독 없는 전파를 깨뜨린다. (↔ 원칙 5)

### C-2. 원천은 requirements·constraints이고, 목업은 파생물이다
목업을 손으로 편집해 원천을 우회 수정하는 경로를 만들지 않는다. 피드백은 대화·요청으로 들어와 requirements·constraints를 고치고, 목업은 거기서 다시 렌더된다. 하류로 나가는 것은 목업 원본이 아니라 시각 계약이다. (↔ 원칙 1)

### C-3. 근거 없는 보완 생성을 허용하지 않는다
requirements·constraints는 대화에 없는 내용을 추가하지 않고, 목업은 요구·제약에 없는 요소를 추가하지 않는다. "사용자 경험을 위해 취소 버튼도 넣어주자" 같은 선의의 보완이 추적 사슬을 끊는다. 부족한 것은 채우지 말고 부족한 채로 두어, 다음 발언으로 들어오게 한다. (↔ 원칙 2)

### C-4. 고도화(수정)는 근거 없이 발생할 수 없다
수정 모드의 입력은 직전 버전과 근거가 된 델타(대화·피드백)로 구조적으로 한정한다. 근거 없이 requirements·constraints가 바뀌거나 삭제되는 경로를 만들지 않는다. (↔ 원칙 3)

### C-5. 대화에 등장한 요청은 반영 없이 휘발되지 않는다
커버리지/누락 체크(요구사항 §3.5)가 잡아낸 요청은, 휴먼 게이트를 거쳐 **채택**(requirement/constraint로 편입)되거나 **명시적 제외**(그 제외 결정이 하나의 constraint가 됨) 중 하나로 귀결되어야 한다. 요청이 아무 반영처 없이 사라지는 것을 금한다. (↔ 원칙 4)

### C-6. 얇은 슬라이스 원칙 — 부수 기능이 core를 복잡화하지 않는다
음성 입력 등 kick·편의 아이템은 핵심 골든패스(요구사항 §1.3)를 복잡하게 만들거나 그 완결성을 위협하지 않는 선에서만 존재한다. 부수 기능을 위해 core에 무거운 설계·생명주기 장치를 도입하지 않는다. (요구사항 §2.2의 "휘발=허용이지 요구 아님", §4 음성 어댑터와 대응)
